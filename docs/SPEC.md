# 【五、已確認核心流程】

1.  建立者設定：

    -   排程主題
    -   自己的名字
    -   總人數
    -   日期範圍
    -   每日時間範圍
    -   會議時長
    -   時區
    -   必填截止時間

2.  總人數包含建立者。

3.  建立者建立排程後，自動成為第一位參與者。

4.  排程一旦建立，所有基本設定立即鎖定，不可修改，包括：

    -   人數
    -   日期
    -   每日時間範圍
    -   會議時長
    -   時區
    -   截止時間

5.  建立者分享排程連結。

6.  其他人開啟連結後輸入自己的顯示名稱即可加入。

7.  同一排程內名字不可重複，且不分大小寫。

8.  額滿或填寫截止後停止新增參與者。

9.  可行時間每格固定 30 分鐘。

10. 時間選擇介面必須支援：

    -   點選
    -   拖曳
    -   逐日切換
    -   清除單日

11. 只有按下「儲存／提交」才算已填寫。

12. 允許提交完全空白的時間，代表此人沒有任何可行時間。

13. 填寫截止時間是唯一結算觸發條件。Server time < deadline 時可重複儲存／修改，最後成功儲存的資料有效；全員提交只代表進度完成，不鎖定、不推薦、不開投票。

14. 截止前只顯示：

    -   已加入人數
    -   已提交人數
    -   目前進度

15. Server time >= deadline 時鎖定可行時間並計算推薦；若只有一個最佳時段：

    -   不投票
    -   直接交由建立者決定是否確認

16. 若有多個並列最佳時段：

    -   系統自動開啟投票
    -   所有並列最佳時段都必須成為候選
    -   不得任意截斷候選
    -   所有人的可行時間已於截止時鎖定

17. 投票採：

    -   單選偏好
    -   每人最多一票
    -   投票結束前可以修改自己的選擇

18. 投票結束規則：

    -   所有目前有效且已加入排程的參與者都完成投票後，由 Server 在最後一票的 transaction 中自動結束投票
    -   前端不得傳入或決定 `allVoted` 狀態
    -   建立者仍可在全員投票前手動提前結束投票

19. 結束投票後：

    -   保留票數
    -   所有投票唯讀，不可再修改
    -   進入等待建立者確認正式時間
    -   不必立即成立會議
    -   建立者可以稍後確認

20. 系統永遠不得自動成立正式會議。

21. 最終時間一定由建立者人工確認。

22. 確認後：

    -   可行時間唯讀
    -   推薦候選唯讀
    -   投票唯讀

23. 建立者可以取消排程。

24. 取消後：

    -   保留所有資料
    -   所有內容唯讀

25. 截止時間到達時，即使尚未全員加入或提交，仍以已加入參與者最後儲存的資料計算；未提交者視為沒有可行時間。推薦的人數分母為已加入參與者人數，建立時的預計總人數另保留於進度。

    -   不允許延長截止時間或更新可行時間；後端拒絕逾期更新。
    -   新排程截止時間必填，且需為未來的有效時區時間。
    -   既有未設定截止時間的排程不自動補值，持續收集且不提前推薦；需新流程時可另建排程。
    -   既有已進入投票／確認／取消的排程保留原狀態，不重新結算。

### Server-side deadline transition

FastAPI 在讀取排程與相關操作時取得 PostgreSQL Schedule row lock，檢查 deadline 並進行冪等結算。所有最佳候選保存於既有 candidate_times，含單一最佳，作為已結算標記；多個才轉為 VOTING。單一最佳保留資料庫 COLLECTING enum，但以已截止且有最佳候選表示「等待建立者確認」，可行時間不可修改。不增加 schema、migration 或背景服務。

結算與既有推薦／投票／待確認通知在同一 transaction 提交。即使觸發結算的是被拒絕的逾期更新，結算仍保留。沒有請求時不主動喚醒服務，下一次讀取或操作會結算；截止驗證始終使用 Server 時間。

# 【六、推薦演算法】

推薦計算必須以 30 分鐘為基本時間格。

依照設定的會議時長，檢查連續時間格。

例如：

會議時長 = 90 分鐘

則一個候選時間必須包含連續：

3 個 30 分鐘時間格。

只有當某位參與者整段時間都標示為可行，才能算該參與者可以參加此候選時段。

對每個合法候選時段計算：

「可完整參加此時段的人數」

可參加人數最多者為最佳時段。

如果多個候選具有相同的最高可參加人數：

全部視為並列最佳。

日期與開始時間只能決定：

顯示順序。

不得用日期較早、時間較早等規則排除並列候選。

若不存在全員共同時間：

仍然顯示最多人可以參加的時段。

並且顯示：

-   可以參加的人
-   無法參加的人

首頁或摘要區可以只顯示前三項推薦。

但：

完整推薦結果以及投票候選不得截斷並列最佳時段。

系統不得替建立者自動選擇最終會議時間。

# 【七、身分與權限】

本系統沒有會員帳號。

使用：

-   安全 Cookie
-   高熵 Token

辨識建立者及參與者。

身分必須以「每一個排程」為作用範圍。

同一瀏覽器開啟分享連結時：

必須保留原本的建立者或參與者身分。

開啟新分頁不得切換身分。

分享連結本身不得包含管理權限。

另一個瀏覽器、無痕環境或其他人的裝置開啟分享連結時，才會看到加入畫面。

介面必須清楚顯示：

-   目前使用者名稱
-   建立者 / 參與者身分

避免使用者誤以為「分享連結 = 登入建立者」。

測試時可以提示使用：

無痕視窗

模擬其他參與者。

但正式參與後應固定使用同一瀏覽器。

系統不得自行：

-   清除 Cookie
-   切換成別人的身分
-   新增會員系統

公開排程識別碼必須不可預測。

Token 必須使用密碼學安全的高熵亂數。

資料庫不得直接保存可使用的原始敏感 Token。

只保存：

-   Hash
-   或適當的 HMAC 結果

私人管理連結使用：

`#token=...`

網址 Fragment。

前端讀取後應立即從網址清除。

再透過同源 POST 將 Token 交給 Server。

Server 驗證後換取：

HttpOnly Cookie。

避免管理 Token 出現在：

-   Server access log
-   Referer
-   一般 URL 紀錄

所有：

-   身分驗證
-   權限
-   截止時間
-   排程狀態
-   輸入驗證

都必須在 FastAPI Server 端重新驗證。

不得只依賴前端。

# 【十一、併發與一致性】

必須正確處理多人同時操作。

至少測試：

## 同時加入最後一個名額

例如：

目前 4 / 5 人。

兩個人同時加入。

結果只能有其中一人成功成為第 5 人。

不得變成 6 / 5。

## 最後一人提交與截止結算

最後一位參與者提交只更新進度；截止前仍能修改。所有提交與截止結算共用 Schedule row lock；多個請求同時到達截止時，只能建立一組一致候選。

## 投票結束

最後兩位參與者同時投票，或建立者手動結束投票的同時若有人投票：

必須確保資料狀態一致。

所有投票 mutation 必須鎖定該 Schedule row。最後一票寫入與「有效參與者票數是否到齊」判斷必須位於同一個 PostgreSQL transaction。自動結束最多發生一次；結束後任何新增或修改投票都必須由 Server 拒絕。自動結束投票不得建立 Meeting。

## 同時確認會議

不得產生兩個不同的正式確認時間。

重要狀態變更必須使用：

-   Database Transaction
-   適當 locking
-   PostgreSQL constraint

保證一致性。

不要只依賴前端按鈕 disabled 防止競態。

## 站內通知

站內通知以 PostgreSQL 正式資料保存，至少包含通知 ID、Schedule、接收 Participant、類型、標題、內容、建立時間與已讀時間。通知接收者必須通過該 Schedule 的 participant HttpOnly Cookie 驗證；不得只憑分享連結讀取通知，也不得跨 Schedule 或讀取其他 Participant 的通知。

通知事件至少包含：排程人數到齊、全員提交可行時間、推薦結果產生、投票開始、投票完成或自動結束、建立者需確認正式時間、正式會議成立、排程取消。建立者專屬行動通知只能送給建立者 Participant；一般參與者只收到狀態通知。

全員提交通知只代表進度，不觸發推薦或投票；一般儲存成功只顯示短暫 Toast，不建立通知、增加未讀數或修改 read state。通知事件與對應狀態 mutation 必須在同一 transaction 建立，並使用 constraint 或等價機制避免競態重複。支援單則已讀與全部已讀；`read_at` 必須持久化，refresh 後仍保持已讀。本階段使用進頁 fetch、mutation 後 refresh 與低頻 polling，不導入 WebSocket、Email 或 Web Push。

# 【十二、安全要求】

必須防止：

-   跨排程操作
-   修改其他人的可行時間
-   修改其他人的投票
-   刪除其他人的留言
-   非建立者確認會議
-   非建立者取消排程
-   非建立者結束投票
-   額滿後加入
-   截止後加入
-   截止後非法修改
-   已確認後修改資料
-   已取消後修改資料
-   可預測 Token
-   Client-side 權限繞過

所有 API 都必須重新驗證：

-   排程 ID
-   Actor identity
-   Actor role
-   Resource ownership
-   Schedule state
-   Deadline
